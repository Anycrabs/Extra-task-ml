# tc_tools — проверка тест-кейсов и форматирование заданий

Два независимо запускаемых модуля:

| Модуль | Запуск | Что делает |
|---|---|---|
| Проверка тест-кейсов | `python -m tc_tools.checker` | Запускает решения на тест-кейсах, сравнивает вывод с эталоном, строит отчёты (`.log`, `.xlsx`) и HTML-дашборд |
| Форматирование заданий | `python -m tc_tools.converter` | По кратким отчётам проверки отбирает верные задания и формирует XML (Moodle, CodeRunner) по шаблону Jinja2 |

> **Важно.** Модуль проверки выполняет код студентов **без изоляции**. Он предназначен для личного
> использования; перед запуском просмотрите решения на наличие необратимых действий
> (удаление и изменение файлов и т. п.).

---

## 1. Установка

Нужен Python **3.10+**.

```bash
pip install -r requirements.txt          # PyYAML, Jinja2, openpyxl
pip install -r requirements-dev.txt      # + pytest, если нужны тесты
```

Модули запускаются из корня проекта (папки, где лежит `README.md`).

## 2. Быстрый старт на примерах

```bash
# 1) проверка: отчёты появятся в out/reports, логи — в out/logs
python -m tc_tools.checker -c configs/check.yaml

# 2) форматирование: XML появится в out/xml
python -m tc_tools.converter -c configs/convert.yaml
```

В `examples/solutions` специально собраны файлы, покрывающие все ветки обработки:

| Файл | Что демонстрирует |
|---|---|
| `М24-512_ИвановИИ__3_1_3.txt` | всё верно; переводы строк CRLF |
| `М24-512_ПетровПП__3_4_6.txt` | неверный вывод (3-5) и ошибка выполнения (3-6); пустая строка внутри решения; символы `< &` в условии |
| `М24-511_СидороваАА__2_1_3.txt` | превышение времени (бесконечный цикл в 2-3); LF |
| `М24-511_КузнецовКК__1_3_4.txt` | задание без тест-кейсов (1-4) → FAILED + предупреждение |
| `М24-512_СмирноваЕЕ__2_4_5.txt` | ошибка оформления в 2-5 (`Решения:` вместо `Решение:`) — задание пропускается, остальные обрабатываются |
| `М24-511_ОрловОО__3_7_9.txt` | в файле задания 7–8, а в имени 7–9 → файл не обрабатывается |
| `М24-512__3_10_10.txt` | группа без фамилии → имя некорректно, файл пропускается |
| `1_1_2.txt` | без группы и студента; переводы строк CR; спецсимволы XML во вводе/выводе |

## 3. Настройка

Все параметры задаются в YAML-файле (`-c файл.yaml`) и/или аргументами командной строки.
Приоритет: **значения по умолчанию ← YAML ← командная строка**. Неизвестный ключ в YAML — ошибка
(защита от опечаток). Полный список аргументов: `python -m tc_tools.checker --help`.

### 3.1. Модуль проверки (`configs/check.yaml`)

| Параметр | Аргумент | По умолчанию | Описание |
|---|---|---|---|
| `inputs` | позиционные | — | Файлы решений и/или папки (из папок берутся `*.txt`) |
| `recursive` | `--recursive` | `false` | Искать во вложенных папках |
| `input_eol` | `--input-eol` | `auto` | Переводы строк во входных файлах: `auto`, `crlf`, `lf`, `cr` |
| `output_eol` | `--output-eol` | `crlf` | Переводы строк в отчётах и логах: `crlf`, `lf`, `cr` |
| `timeout` | `--timeout` | `5` | Ограничение времени на один ТК, с |
| `jobs` | `--jobs` | `4` | Сколько заданий проверять параллельно |
| `python` | `--python` | текущий | Интерпретатор для запуска решений |
| `reports_dir` | `--reports-dir` | `reports` | Папка отчётов |
| `log_dir` | `--log-dir` | `logs` | Папка логов |
| `xlsx` | `--xlsx / --no-xlsx` | `true` | Создавать сводный отчёт |
| `dashboard` | `--dashboard / --no-dashboard` | `true` | Создавать HTML-дашборд |
| `tc_all_skip_passed` | `--tc-all-skip-passed` | `false` | Не включать в `_tc_all.log` файлы без ошибок |
| `groups` | `--group` (повторяемый) | `[]` | Фильтр сводного отчёта/дашборда по группам |
| `students` | `--student` (повторяемый) | `[]` | Фильтр по студентам (`ФамилияИО`) |
| `file_numbers` | `--file-number` (повторяемый) | `[]` | Фильтр по номерам файлов с заданиями |

### 3.2. Модуль форматирования (`configs/convert.yaml`)

| Параметр | Аргумент | По умолчанию | Описание |
|---|---|---|---|
| `inputs`, `recursive`, `input_eol`, `output_eol`, `log_dir` | | | как в модуле проверки |
| `reports` | `--reports` (повторяемый) | `[]` | Файлы `Отчет_<Метка>_all.log` и/или папки с ними |
| `ignore_reports` | `--ignore-reports` | `false` | Выгрузить все задания без учёта проверки |
| `topics` | `--topics` | `null` | Справочник тем (CSV) |
| `template` | `--template` | `tc_tools/templates/moodle_coderunner.xml.j2` | Шаблон Jinja2 |
| `split_by_topic` | `--split-by-topic` | `false` | Отдельный XML на каждую тему |
| `output_name` | `--output-name` | см. ниже | Шаблон имени: `{topic}`, `{topic_title}`, `{timestamp}` |
| `output_dir` | `--output-dir` | `xml` | Папка для XML |

Имя по умолчанию: `Questions_all_{timestamp}.xml` (один файл) или `Questions_{topic}_{timestamp}.xml`
(по темам). `{topic}` и `{topic_title}` без `split_by_topic` — ошибка настроек.

### 3.3. Примеры командной строки

```bash
# проверить два файла с лимитом 2 с, без xlsx
python -m tc_tools.checker М24-512_ИвановИИ__3_1_3.txt 1_1_2.txt --timeout 2 --no-xlsx

# сводный отчёт только по группе М24-512 и файлу 3
python -m tc_tools.checker -c configs/check.yaml --group М24-512 --file-number 3

# во входных файлах допускать только LF, отчёты писать в LF
python -m tc_tools.checker examples/solutions --input-eol lf --output-eol lf

# XML по темам с названием темы в имени файла
python -m tc_tools.converter -c configs/convert.yaml --split-by-topic \
    --output-name "Тема_{topic}_{topic_title}_{timestamp}.xml"

# XML без учёта результатов проверки
python -m tc_tools.converter examples/solutions --ignore-reports --topics examples/topics.csv
```

Коды завершения: `0` — успешно, `1` — ошибка выполнения (нет входных файлов, ошибка шаблона),
`2` — ошибка настроек.

## 4. Результаты

### 4.1. Модуль проверки

Все файлы одного запуска имеют одну метку времени `ГГГГММДД-ЧЧММСС`.

| Файл | Содержимое |
|---|---|
| `Отчет_<Метка>_all.log` | Краткий отчёт: статус файла и каждого задания. Читается модулем форматирования |
| `Отчет_<Метка>_tc_all.log` | Подробный отчёт по всем ТК |
| `Отчет_<Метка>_tc_failed.log` | Подробный отчёт только по ошибочным ТК |
| `Отчет_<Метка>_results.xlsx` | Сводка (лист «Сводка» по требованиям) + лист «Задания» со статусом каждого задания и причиной ошибки |
| `Отчет_<Метка>_dashboard.html` | HTML-дашборд (дополнительно) |
| `Check_log_<Метка>.log` | Лог работы |

Фрагмент подробного отчёта:

```
3: FAILED  [М24-512_ПетровПП__3_4_6.txt]
    3-5: FAILED
        Решение:
            s = input()
            print(len(s))
        =>ТК-3: FAILED
            Ввод:
                -4567
            Вывод:
                5
            Эталон:
                4
```

### 4.2. HTML-дашборд

Самодостаточный файл (без интернета и внешних библиотек), светлая и тёмная тема.

* KPI: студенты, файлы, верные задания, % верных, пройденные ТК;
* кольцевая диаграмма исходов ТК: пройдено / неверный вывод / ошибка / превышено время;
* гистограмма распределения файлов решений по % верных заданий;
* % верных по группам и по файлам с заданиями (темам);
* таблица студентов: поиск, фильтр по группе, сортировка по клику на заголовок,
  «мозаика» заданий (зелёный/красный квадрат, подсказка при наведении).

Дашборд учитывает те же фильтры (`groups`, `students`, `file_numbers`), что и xlsx-отчёт.

### 4.3. Модуль форматирования

`Questions_*.xml` и `Conversion_log_<Метка>.log`. По завершении в консоль и лог выводится статистика:
обработанные файлы, темы, созданные XML, вопросы (всего и по темам), исключённые задания
(всего и по причинам: не прошли проверку, отсутствуют в отчёте, ошибки обработки).

## 5. Шаблон XML

`tc_tools/templates/moodle_coderunner.xml.j2` — Moodle XML, тип вопроса CodeRunner (`python3`).

* Каждая тема — категория вопросов Moodle `$course$/top/Тема 3. Циклы` (без справочника — `Тема 3`).
* Вопрос: название `3-5. Название`, `idnumber` = номер задания, текст = условие + описания ввода/вывода,
  эталонное решение в `<answer>`, все тест-кейсы в `<testcases>`.
* Первые **3** ТК: `useasexample="1"`, `display=SHOW` — видны студенту как примеры;
  остальные `useasexample="0"`, `display=HIDE`. При проверке используются все ТК.
* Экранирование: окружение Jinja2 создаётся с `autoescape=True`, поэтому каждое значение `{{ ... }}`
  экранируется (`& < > " '`). HTML-текст вопроса лежит внутри `CDATA`: разметку (`<div>`, `<p>`)
  задаёт шаблон, а экранированный текст задания отображается как обычный текст.
* `StrictUndefined`: опечатка в имени переменной шаблона — явная ошибка, а не пустая строка.
* После заполнения шаблона XML проверяется на корректность (`xml.etree`), ошибка пишется в лог.

### Данные шаблона

| Переменная | Тип | Описание |
|---|---|---|
| `generated_at` | `str` | Метка времени |
| `topics` | `list` | Темы в данном XML (при разбиении — одна) |
| `topic.number` / `topic.title` | `str` / `str \| None` | Номер и название темы |
| `topic.questions` | `list` | Вопросы в порядке номеров заданий |
| `question.id`, `.title`, `.condition`, `.input_description`, `.output_description`, `.solution` | `str` | Поля задания |
| `question.test_cases` | `list` | ТК: `number` (`int`), `input`, `output` (`str`, строки через `\n`) |

## 6. Архитектура

```
tc_tools/
├── common/                  общий код обоих модулей
│   ├── constants.py         PASSED/FAILED, префикс имён отчётов
│   ├── textio.py            чтение/запись UTF-8, проверка и нормализация переводов строк
│   ├── naming.py            regex имени файла решений, номер задания, метка времени, имена отчётов
│   ├── discovery.py         сбор файлов из списка путей/папок
│   ├── parser.py            файл решений → задания (разбор + проверка диапазона)
│   ├── config.py            YAML + аргументы командной строки, валидация
│   └── logsetup.py          лог в файл с нужными переводами строк + консоль
├── checker/                 модуль проверки
│   ├── __main__.py          аргументы командной строки, точка входа
│   ├── pipeline.py          оркестрация: чтение → проверка → отчёты
│   ├── runner.py            запуск решения на ТК, сравнение вывода
│   ├── reports.py           _all.log, _tc_all.log, _tc_failed.log, _results.xlsx
│   └── dashboard.py         агрегаты для HTML-дашборда
├── converter/               модуль форматирования
│   ├── __main__.py
│   ├── pipeline.py          оркестрация: чтение → отбор → темы → XML → статистика
│   ├── reports_reader.py    разбор кратких отчётов, выбор самой поздней проверки
│   ├── topics.py            справочник тем (CSV)
│   └── render.py            Jinja2, проверка XML, шаблон имени файла
└── templates/
    ├── moodle_coderunner.xml.j2
    └── dashboard.html.j2
```

Поток данных модуля проверки:

```
файлы/папки ─collect_files─► пути ─load_solution_file─► файлы с заданиями
    ─check_files (пул потоков, по процессу Python на каждый ТК)─► результаты
    ─► brief_report / detailed_report / write_results_xlsx / render_dashboard
```

**Принципы, которые стоит знать для защиты:**

1. **Функциональный стиль.** Классов нет; данные — обычные словари (ключи описаны в docstring).
   Большинство функций чистые (вход → выход), побочные эффекты (файлы, процессы, лог) собраны
   в `pipeline.py`. Поэтому функции легко тестировать по отдельности.
2. **Общий парсер.** Оба модуля читают файлы решений одним и тем же кодом (`common/parser.py`),
   поэтому одинаково трактуют формат.
3. **Внутри программы переводы строк — всегда `\n`.** Формат проверяется при чтении
   (`split_lines`), а нужный формат применяется при записи (параметр `newline` функции `open`,
   который заменяет каждый `\n`). Тот же приём используется для файла лога — так многострочные
   сообщения и traceback тоже получают нужный формат.
4. **Изоляция запусков.** Каждый ТК — отдельный процесс `python -X utf8 solution.py` с таймаутом
   (`subprocess.run(timeout=...)`). Текущая папка — временная папка задания, она удаляется
   после проверки. `-X utf8` гарантирует UTF-8 на Windows.
5. **Параллельность.** Задания проверяются в `ThreadPoolExecutor`: потоки лишь ждут дочерние
   процессы, поэтому GIL не мешает. `pool.map` сохраняет порядок — отчёты детерминированы.
   При `jobs: 1` проверка последовательная.

### Разбор файла решений

1. Имя файла проверяется регулярным выражением; имя нормализуется в NFC (macOS хранит «й», «ё»
   в разложенном виде).
2. Строки делятся на блоки по **двум и более** пустым строкам подряд.
3. Блок разбирается последовательно: поля идут в фиксированном порядке, каждое поле продолжается
   до строки, начинающейся со **следующего** ключевого слова; решение — до `==Тест-кейсы==`.
4. Тест-кейсы: `=>ТК-N` (нумерация с 1 подряд), `Ввод:` до `Вывод:`, `Вывод:` до следующего `=>ТК-`.
5. Номера заданий сверяются с диапазоном из имени файла.

## 7. Решения по неоднозначным местам ТЗ

| Ситуация | Решение |
|---|---|
| Номера заданий «не совпадают с диапазоном» | Множество номеров в файле должно **точно** совпадать с диапазоном из имени (нет лишних, недостающих и повторов). Иначе файл не обрабатывается |
| Некорректно оформленное задание в корректном файле | Не выполняется, ошибка в логе. В отчётах проверки учитывается как **FAILED** (комментарий «ошибка оформления»), чтобы не завышать % верных. В модуле форматирования считается «ошибкой обработки» |
| Нет строки `==Тест-кейсы==` | Ошибка оформления. Есть строка, но нет ТК — задание FAILED с предупреждением (по ТЗ) |
| Пустые строки в конце значений ТК | Удаляются (это оформление файла, а не данные) |
| Пустой эталон и вывод `print()` | Совпадают: после удаления завершающего перевода строки оба — пустая строка |
| `=>TK-1` латиницей | Допускается наравне с `=>ТК-1` (частая опечатка) |
| Несколько кратких отчётов | Применяются по возрастанию метки времени, для каждого задания побеждает **самая поздняя** проверка. Задания, проверенные только в старых запусках, не теряются |
| Одинаковый номер файла у разных студентов в `_all.log` | Формат строки сохранён по ТЗ; модуль форматирования опирается на номер задания (он уникален). В подробных отчётах после статуса добавлено имя файла решений |
| Фильтры по группам/студентам/файлам | Применяются к xlsx и дашборду. `_all.log` всегда полный — он нужен модулю форматирования |
| Справочник тем с ошибкой в строке | Файл целиком считается некорректным (п. 3.7 ТЗ): ошибка в лог, используются номера тем |
| `/` в названии темы | В пути категории Moodle удваивается (`//`), как требует Moodle |
| BOM в начале UTF-8 файла | Допускается при чтении |

## 8. Тесты

```bash
python -m pytest -q
```

45 тестов: переводы строк, разбор имён и файлов решений, все статусы проверки (верно, неверный
вывод, ошибка, таймаут, нет ТК), сортировка и фильтры отчётов, справочник тем, выбор самого
позднего отчёта, экранирование и примеры в XML, сквозные запуски обоих модулей.
